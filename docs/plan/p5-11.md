# P5-11 — Ce qui bloque, et découpage proposé

Note de travail de la branche `refonte/p5-11-sources-locales` (à retirer avant de passer la PR à prête).

La tâche demande de s'arrêter et de l'écrire si le socle des plugins de code (SDK, hôte, contexte, pont des
sources) ne permet pas l'extraction. C'est le cas : voici les manques constatés sur `main` (38466b2), puis le
découpage proposé. Rien n'a été modifié dans le socle ni dans le SDK.

## Manques du socle

| # | Manque | Où | Conséquence si on extrait quand même |
| --- | --- | --- | --- |
| M1 | Une source de plugin ne reçoit **aucun emplacement** : le pont appelle `scan(null)` et range ses éléments sous une seule instance par contribution (`instance: e.id`). | `src/main/plugins/bridges.ts` (en-tête : « la source reçoit `null` en attendant ») | Le dossier local et le partage réseau ne savent pas quels dossiers analyser ; un seul emplacement par plugin au catalogue. |
| M2 | Les clés des éléments d'un plugin `code` sont préfixées `plugin:<id>\|`. | `checkElements` (`bridges.ts`) | Les éléments `local:<chemin>` d'aujourd'hui changent de clé : réglages par élément, infos en ligne, listes, reprise de lecture et historique ne les retrouvent plus. Contraire à « bibliothèque retrouvée telle quelle ». |
| M3 | Les images d'un élément de plugin doivent être des adresses `http(s)`. | `checkElements` | Affiches et fonds trouvés à côté des fichiers (`cover.jpg`, `film-poster.jpg`, `fanart.jpg`) perdus. |
| M4 | Aucune nature de contribution pour les **sous-titres** (liste fermée `CODE_CONTRIBUTIONS`). Les sous-titres sont demandés à la lecture (`api.subtitles(path)` → `findSubtitles`), pas à l'analyse. | `packages/plugin-sdk/src/manifest.ts`, `contributions.ts` | `src-subs` ne peut pas devenir un plugin sans une nouvelle nature dans le SDK (et son pont dans le cœur). |
| M5 | Une règle de continuité ne peut pas **accorder de dossiers** au plugin qu'elle active (pas de champ `folders`). | `src/main/config/migrations/continuity.ts`, `src/main/plugins/continuity.ts` | Après la mise à jour, le plugin n'a le droit de lire aucun des dossiers déjà configurés. |
| M6 | Quand l'utilisateur ajoute un dossier à la bibliothèque (Réglages, `config.library.sources`), rien ne l'accorde au plugin ; `files.requestFolder` suppose un écran du plugin, et la tâche n'en ajoute pas. | Réglages de la bibliothèque, `state.folders` | Un dossier ajouté après la mise à jour ne serait jamais analysé. |
| M7 | Bornes du pont plus basses que la bibliothèque : 50 000 éléments et 60 s par analyse (`BRIDGE_LIMITS`), 50 000 fichiers par `walk` ; la bibliothèque en accepte 150 000 (`MAX_ITEMS`) sans délai. | `bridges.ts`, `context.ts` | Une grosse bibliothèque ou un NAS lent perd des éléments ou toute son analyse. |
| M8 | `walk` ne rend que des fichiers (chemin, taille, date) : pas d'option pour ignorer les dossiers cachés et `$…` comme `walkLibrary`. | `context.ts` | Différence de résultat (à filtrer dans le plugin : faisable, mais à vérifier). |

Le partage réseau, lui, n'a pas besoin de « Réseau local » : un partage `smb://`, `\\NAS\…` ou `//NAS/…` est lu
comme un dossier monté par le système (`location.ts`). La permission `localNetwork` du contexte ne couvre que le
HTTP vers le réseau local. Avec M1 à M6 réglés, `code` + `folders` suffirait ; sans M2, seul `privileged` garde
les clés.

## Choix à trancher avant d'écrire le code

1. **Clés (M2)** : soit les trois plugins sont `privileged` (inclus, pas de préfixe ; mais du code dans le processus
   principal pour lire des dossiers, ce qui va contre « le niveau le plus bas »), soit le pont accepte, pour un
   plugin `code`, des clés `local:<chemin>` dont le chemin est dans ses dossiers accordés (la clé est alors vérifiée
   comme `open.path`), soit une migration réécrit les clés existantes (lourd : catalogue, listes, historique,
   réglages par élément).
2. **Emplacements (M1, M6)** : les emplacements restent dans `config.library.sources` (le cœur les garde, les
   accorde au plugin qui les gère et les lui passe un par un : `scan(location)`, une instance par emplacement), ou
   ils deviennent un réglage `list` du plugin (déplacement de réglages par la continuité, mais les types par
   emplacement — vidéo, musique, images — n'ont pas d'équivalent dans les réglages de plugin).
3. **Sous-titres (M4)** : nouvelle nature `subtitles` dans le SDK (`find(videoPath) → { label, lang, vtt }[]`, appelée
   à la lecture, le cœur ne transmettant qu'un chemin déjà autorisé par sa politique d'accès), ou bien les
   sous-titres restent au cœur et l'inventaire passe `src-subs` en « Cœur ».

## Découpage proposé

1. **P5-11a — socle** (PR Mire seule, avec le SDK si accord) : M1 (emplacements passés à la source, une instance
   par emplacement), M3 (images locales dans les dossiers accordés), M5 (dossiers accordés par une règle de
   continuité), M6 (dossier ajouté → accordé au plugin qui le gère), M7 (bornes), et la décision sur M2 ; tests avec
   une source factice.
2. **P5-11b — sous-titres** : nature `subtitles` (SDK + pont), plugin inclus `mire.subtitles` (code, `folders`),
   règle de continuité.
3. **P5-11c — dossier local** : plugin inclus `mire.source.local` (code, `folders`), retrait de `localProvider` pour
   les dossiers, règle de continuité avec les dossiers déjà autorisés.
4. **P5-11d — partage réseau** : plugin inclus `mire.source.network` (code + `folders`, ou `privileged` selon la
   décision 1), justification du niveau, vérification à la main sur un vrai NAS.

P5-12 (serveur web, liste M3U) dépend de P5-11a, pas des trois autres.
